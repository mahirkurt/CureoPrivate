# RFC v1.1: Transport Layer Abstraction

> Status: **Accepted & Shipped** (v1.1.0 GA) · 2026-05-27
> Target sürüm: **v1.1.0** — shipped across alpha.1 → alpha.2 → beta.1 → GA
> Author: figma-forge maintainers
> Affects: 7 previously-deferred orchestrate stages; new public API surface

## 1. Motivation

`figma-forge` v1.0.0 ships **12 modes**, of which **5** execute purely on
local artifacts (audit, diff, trend, manifest, sign/verify) and **1** executes
through the operator's clipboard (auto-remediate plugin channel). The
remaining **6 modes** declare their intent in the orchestration manifest
but defer real execution:

| Mode               | Today (v1.0.0)              | Goal in v1.1                          |
|--------------------|------------------------------|---------------------------------------|
| SCAFFOLD           | logs "would have executed"   | Creates real Figma files              |
| FOUNDATIONS_BUILD  | logs                          | Writes Variables + paint/text styles  |
| COMPONENTS_BUILD   | logs                          | Creates variant components            |
| ICONS_BUILD        | logs                          | Imports SVG → ComponentNode           |
| PATTERNS_BUILD     | logs                          | Creates composite components          |
| CODE_CONNECT       | logs                          | Attaches mappings to components       |
| PUBLISH            | logs                          | Publishes library                     |

Each operation hits Figma through one of several radically different
channels (Figma REST API, the Figma Plugin runtime, MCP servers, raw
clipboard). Each channel has different authentication, capabilities,
latency profiles, error shapes, and idempotency guarantees.

**Without an abstraction layer**, every mode would either:

1. Pick one channel and hard-couple the implementation to it (sacrificing
   reachability — Enterprise-plan-only REST cuts off all non-Enterprise
   users), or
2. Embed channel branching throughout the codebase (sacrificing
   maintainability — every new transport requires modifying every mode).

The **transport layer** is the abstraction that gives v1.x users a single
high-level interface — `ff.run_pipeline(library_dir, transport=...)` —
while internally selecting the best-available channel for each operation.

## 2. Goals & Non-Goals

### 2.1 In scope

- A `TransportAdapter` Python Protocol that captures the **minimum
  sufficient operation set** for the 7 deferred modes
- At least **three concrete adapter implementations**:
  - `StubTransport` — always-available fallback; emits structured log
  - `PluginCaptureTransport` — accumulates operations into a TypeScript
    script the operator pastes (continuation of v0.3's plugin channel)
  - `RestTransport` — calls Figma REST API; covers Variables fully,
    other operations limited per Figma's REST capability matrix
- A **capability matrix** declared in code (machine-readable) that
  documents which adapter supports which operation
- A **router strategy** that selects per-operation adapter based on
  operator preference + capability availability
- An **error model** that normalizes channel-specific errors into a
  single `TransportError` hierarchy
- An **idempotency model** that guarantees safe re-runs even when the
  underlying channel doesn't (plugin scripts duplicate components on
  re-run unless explicitly guarded; the v1.1 layer adds the guard)

### 2.2 Out of scope for v1.1

- **Live MCP transport** — Figma MCP server's writable surface is in
  flux; the MCP adapter is deferred to v1.2 once Figma stabilizes
  the resource model. v1.1 ships only the Protocol stub for it.
- **Bidirectional sync** — v1.1 is one-way (source-of-truth → Figma).
  Figma → source-of-truth diff/pull is a v2.x concern.
- **Real-time collaboration awareness** — v1.1 does not coordinate
  with active editing sessions; concurrent edits during pipeline runs
  produce undefined behavior (consistent with operator's expectation).
- **Cost / rate-limit management** — REST API has per-token rate
  limits; v1.1 logs the limits but doesn't queue or back off. v1.2
  introduces a `BackoffPolicy` abstraction.

## 3. Operation Set

Distilled from the 7 deferred modes; **22 operations** the transport
layer must support. The Protocol is shaped so each operation has a
clear pre/post-condition and is independently mock-able.

### 3.1 File-level operations

```python
def create_file(self, *, name: str, file_kind: FileKind) -> FileRef:
    """SCAFFOLD: create an empty Figma file. Returns its key."""

def get_file(self, *, key: str) -> FileRef:
    """Locate an existing file; raises NotFoundError if absent."""

def publish_library(
    self, *, file_key: str, changelog: str
) -> PublishRef:
    """PUBLISH: publish all components/styles for library consumption."""
```

### 3.2 Variable-collection operations (FOUNDATIONS_BUILD core)

```python
def create_variable_collection(
    self, *, file_key: str, name: str, modes: list[str]
) -> CollectionRef: ...

def get_variable_collection(
    self, *, file_key: str, name: str
) -> CollectionRef | None: ...

def create_variable(
    self, *, collection_ref: CollectionRef,
    name: str, type: VariableType,
    values_per_mode: dict[str, VariableValue],
) -> VariableRef: ...

def update_variable(
    self, *, variable_ref: VariableRef,
    values_per_mode: dict[str, VariableValue],
) -> None: ...

def create_alias_reference(
    self, *, source_var: VariableRef, target_var: VariableRef,
    mode_id: str,
) -> None: ...
```

### 3.3 Style operations (FOUNDATIONS_BUILD secondary)

```python
def create_paint_style(
    self, *, file_key: str, name: str, paints: list[Paint]
) -> StyleRef: ...

def create_text_style(
    self, *, file_key: str, name: str, properties: TextStyleProperties
) -> StyleRef: ...

def create_effect_style(
    self, *, file_key: str, name: str, effects: list[Effect]
) -> StyleRef: ...
```

### 3.4 Component operations (COMPONENTS_BUILD + ICONS_BUILD + PATTERNS_BUILD)

```python
def create_page(self, *, file_key: str, name: str) -> PageRef: ...

def create_component(
    self, *, page_ref: PageRef,
    name: str, geometry: ComponentGeometry,
) -> ComponentRef: ...

def create_component_set(
    self, *, page_ref: PageRef, name: str,
    variants: list[VariantSpec],
) -> ComponentSetRef: ...

def set_component_property(
    self, *, component_ref: ComponentRef,
    key: str, value: Any,
) -> None: ...

def import_svg_as_component(
    self, *, page_ref: PageRef,
    name: str, svg_source: str,
    canonical_size: tuple[int, int],
) -> ComponentRef: ...

def update_component_description(
    self, *, component_ref: ComponentRef,
    description: str, doc_links: list[str],
) -> None: ...
```

### 3.5 Code Connect operations

```python
def attach_code_connect(
    self, *, component_ref: ComponentRef,
    mapping: CodeConnectMapping,
) -> CodeConnectRef: ...

def list_code_connect(
    self, *, file_key: str
) -> list[CodeConnectRef]: ...
```

### 3.6 Identification & introspection

```python
def supports(self, operation_name: str) -> bool:
    """Capability query: does this adapter implement the named op?"""

def adapter_id(self) -> str:
    """Stable identifier for the adapter (e.g. 'rest-v1', 'plugin-capture')."""

def authentication_required(self) -> AuthRequirement:
    """Declares whether/what credentials are needed."""
```

### 3.7 Lifecycle

```python
def begin_session(self) -> SessionToken: ...
def commit_session(self, token: SessionToken) -> SessionResult: ...
def rollback_session(self, token: SessionToken) -> None: ...
```

Session scoping lets a pipeline batch all operations and commit them
atomically (REST adapter buffers and ships them in one POST batch;
plugin adapter accumulates the TypeScript and emits a single script;
stub adapter logs them).

## 5. Router Strategy

The router picks an adapter per operation based on:

1. **Operator preference** — manifest declares
   `transport_preferences: ["rest", "plugin-capture", "stub"]` in
   priority order. First adapter that `supports()` the operation wins.

2. **Capability availability** — when no preferred adapter supports
   the operation, the router falls back through the preference list;
   if every adapter in the preference list lacks the capability, the
   stub adapter is selected as last resort and a warning is logged.

3. **Authentication availability** — when an adapter `supports()`
   but the required credentials are absent, it's skipped and the next
   preferred adapter is tried. Adapters declare auth requirements via
   `authentication_required()`.

Example manifest fragment:

```jsonc
{
  "transport_preferences": ["rest", "plugin-capture"],
  "transport_credentials": {
    "rest": {
      "figma_pat_env": "FIGMA_PERSONAL_ACCESS_TOKEN"
    }
  }
}
```

For `create_variable_collection`: REST wins (Enterprise PAT present).
For `create_component`: REST doesn't support; falls through to
`plugin-capture` which accumulates the operation into a TypeScript
script the operator runs at the end.

## 6. Authentication & Credentials

| Adapter              | Authentication needed        | Source                                              |
|----------------------|------------------------------|-----------------------------------------------------|
| `StubTransport`      | none                         | —                                                   |
| `PluginCapture`      | none                         | —                                                   |
| `RestTransport`      | Figma Personal Access Token  | `FIGMA_PERSONAL_ACCESS_TOKEN` env var                |
| `McpCursorTransport` | active Cursor MCP session    | ambient (Cursor IDE manages)                        |

**Secret handling rule**: figma-forge **never logs** credential values
and **never writes them** to manifest/provenance artifacts. The
manifest contains the env-var **name**, not the value.

## 7. Error Model

A normalized exception hierarchy under `figma_forge.transport.errors`:

```
TransportError                       (base)
├── AuthenticationError              (PAT missing/invalid)
├── AuthorizationError               (PAT lacks scope; e.g. non-Enterprise)
├── NotFoundError                    (file/variable/collection absent)
├── ValidationError                  (operation arg violates Figma's rules)
├── ConflictError                    (idempotency conflict; e.g. name already exists)
├── RateLimitError                   (transport-specific; carry retry-after)
├── CapabilityUnsupportedError       (adapter doesn't support operation)
└── UpstreamUnavailableError         (channel down — sigstore offline, etc.)
```

Adapter implementations translate channel-specific errors:

- REST `400/401/403/404/409/429/5xx` → mapped per HTTP semantics
- Plugin (capture mode) → emits compile-time errors when the
  TypeScript fails type-check; `ValidationError` raised
- Stub → never raises; always succeeds (this is the contract)

## 8. Idempotency

The pipeline runs are **assumed safe to re-execute** by the operator.
Each operation must therefore be idempotent under "same arguments
applied twice produces the same end state".

| Adapter         | Idempotency mechanism                                     |
|-----------------|-----------------------------------------------------------|
| `Stub`          | trivially idempotent (no state)                           |
| `PluginCapture` | TS script checks for existing nodes by name before creating |
| `Rest`          | uses `GET ... → if absent → POST` two-step pattern        |
| `MCP-Cursor`    | depends on MCP server; defer guarantee to v1.2            |

The plugin adapter inherits the v0.3.1 G14 "idempotent re-run" pattern:
`findOne(ComponentNode, name=...)` before creating; update in-place
when present.

## 9. Public API Additions (v1.1)

The following identifiers are added to `figma_forge.__all__` at v1.1.0;
they are **stable from v1.1.0 onwards** per the v1.x API contract:

```python
import figma_forge as ff

# Transport selection
ff.StubTransport
ff.PluginCaptureTransport
ff.RestTransport

# Protocol & types
ff.TransportAdapter
ff.TransportError
ff.AuthenticationError
ff.CapabilityUnsupportedError

# High-level pipeline
ff.run_pipeline(library_dir, *, transport=...)
```

All existing v1.0 identifiers retain their signature and semantics —
no breaking changes. The router and capability matrix are
implementation details accessed only via `TransportAdapter`.

## 10. Migration Plan

### 10.1 v1.0 → v1.1.0-alpha

Zero breaking changes. New optional kwargs to `orchestrate`:

```python
# v1.0 (still works in v1.1):
orchestrate(manifest, library_dir)

# v1.1 new:
orchestrate(manifest, library_dir, transport=ff.RestTransport(pat=...))
```

When `transport=` is omitted, defaults to `StubTransport()` — preserves
v1.0 behavior bit-for-bit (modes still log, never execute).

### 10.2 v1.1.0-alpha → v1.1.0 GA

- Implement the **5 most-impactful** REST operations end-to-end
  (Variables collection, variable, mode, alias; get file)
- Implement the **PluginCapture full operation set** end-to-end
- Ship a **smoke test** running the pipeline against Düstur with both
  RestTransport (mocked) and PluginCaptureTransport
- Document `FIGMA_PERSONAL_ACCESS_TOKEN` requirement and Enterprise
  plan caveat in `references/`

### 10.3 v1.1.0 → v1.2.0

- Live MCP transport (Cursor MCP, Anthropic MCP)
- Backoff policy & rate-limit awareness
- Real-time concurrency detection (warn when operating on a file with
  active editors)

## 11. Risks & Open Questions

### 11.1 Risk: REST API capability cliff

Figma REST API supports Variables (Enterprise plan) but not styles,
not components, not pages. A `RestTransport`-only pipeline can build
foundations but cannot build components. The router's fallback to
PluginCapture is the mitigation; the operator gets a TS script for
the component half.

### 11.2 Risk: Plugin channel UX friction

PluginCapture emits a TS script the operator must paste into Figma's
plugin console. This is interactive — incompatible with fully-headless
CI. Mitigation: ship the script with clear instructions and a
`continue_on_failure` mode in CI that proceeds past component stages.

### 11.3 Open question: MCP server capability evolution

Figma's MCP server is in active development. The `McpCursorTransport`
adapter is shipped as a Protocol stub in v1.1; concrete implementation
deferred to v1.2 once Figma stabilizes the MCP write surface.

### 11.4 Open question: token reusability across sessions

Should `RestTransport` cache the PAT in process memory for the
pipeline run, or re-read it from env on every operation? Decision:
read once at construction time; reject env-var mutation mid-pipeline.

### 11.5 Open question: deterministic ordering

Does the router guarantee operations are applied in manifest order,
or may it reorder for efficiency (e.g. batch all create_variable calls
into one POST)? Decision: declare insertion order as observable;
batching is internal to the adapter and must preserve final state.
