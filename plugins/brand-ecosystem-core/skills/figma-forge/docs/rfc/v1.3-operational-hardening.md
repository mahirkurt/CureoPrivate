# RFC v1.3: Transport Layer Operational Hardening

> Status: **Accepted & Shipped** (v1.3.0 GA) · 2026-05-28
> Target sürüm: **v1.3.0** — shipped across alpha.1 → alpha.2 → beta.1 → GA
> Author: figma-forge maintainers
> Supersedes the v1.3 roadmap items in RFC v1.2 §5

## 1. Motivation

RFC v1.1 and RFC v1.2 built the transport layer's architectural
foundations — adapters, capability matrix, plan emit, backoff,
concurrency. They answered *"what dispatch channels exist and what
can each one do?"* RFC v1.3's question is different: **"how do we
operate this in production?"**

Three specific gaps stood between v1.2's architecture and
production-grade operations:

1. **The emitted MCP plan was unconsumed.** `render_mcp_plan()`
   produced a well-formed 265-step envelope, but how an agent should
   validate it before execution and what semantics it should follow
   during execution were undocumented. Each operator/agent
   re-invented this.
2. **MCP dispatch had three-place drift.** Promoting one operation
   from `use_figma_nl` to `native` (when Figma shipped a new
   granular MCP tool) required coordinated edits across
   `mcp_cursor.py`, `capability_matrix.py`, and `plan_validation.py`
   — one of them being forgotten created silent dispatch drift.
3. **REST dispatch was strictly serial.** A typical Düstur build
   queued ~90 POSTs against Figma's REST API; each was sent and
   awaited individually, multiplying network latency by call count.

This RFC records the design and acceptance of three features that
close these gaps, plus one infrastructure milestone for the test
fixtures that enabled the third feature.

## 2. Features shipped

### 2.1 `validate_mcp_plan` + `PlanValidationReport` (alpha.1)

A pure-Python static validator for the MCP tool-call plan envelope
produced by `McpCursorTransport.render_mcp_plan()`. The validator is
**strict on schema, soft on ordering**:

- **Schema errors** (block execution): envelope must be a JSON
  object with required fields (`plan_format_version`, `adapter`,
  `step_count`, `steps`); `step_count == len(steps)`; per-step
  required fields; valid `mechanism`; monotonic step numbers;
  native steps carry no `instruction`; `use_figma_nl` steps carry a
  non-empty one.
- **Argument errors** (block execution): native steps must carry
  every argument key the named MCP tool expects (enforced from the
  registry of 5 native MCP tools — see §2.2).
- **Ordering warnings** (do not block): heuristic checks that
  dependency-creating steps precede their references
  (`create_variable_collection` before `create_variable`;
  `create_component` before `place_instance`; `create_page` before
  component-on-page steps). False positives are possible on
  cross-session plans, so warnings are advisory.

`is_executable` becomes `False` iff schema or argument errors
present; ordering warnings never block. Accepts either a JSON string
or a pre-parsed dict; never raises for plan content.

Public API additions: `validate_mcp_plan`, `PlanValidationReport`
(38 → 38 symbols counts the alpha.1 additions independently — see
§3).

### 2.2 MCP dispatch registry (alpha.2)

Eliminates the three-place drift. A new internal module
`transport/mcp_dispatch.py` defines `McpDispatchSpec` and a
`REGISTRY` dict (20 entries: 5 native + 15 `use_figma_nl`) — the
**single source of truth** for how every transport operation
dispatches through the Figma MCP server. Three downstream consumers
derive their behavior at import time:

1. **`mcp_cursor._MCP_TOOL_FOR_OPERATION`** — dict-comprehension over
   `REGISTRY`. Identical runtime contents to v1.2; registry-sourced.
2. **`capability_matrix.CAPABILITY_MATRIX`** — `_apply_registry_overrides()`
   overrides every MCP-Cursor cell whose operation is in the registry.
   Other adapters' literal cells remain.
3. **`plan_validation._NATIVE_TOOL_REQUIRED_ARGS`** —
   `native_required_args()` derives the mcp_tool → required_args map.

Promotion from `use_figma_nl` to `native` is now a **one-line registry
edit**; the three consumers re-derive at import. 12 consistency tests
guarantee drift cannot silently re-enter. **Pure internal refactor —
zero public API changes (38 → 38).** The registry itself is
intentionally not exported; figma-forge maintainers edit it and ship
a release, runtime mutation is not supported.

### 2.3 `BatchPolicy` parallel dispatch (beta.1)

Opt-in parallel dispatch for `RestTransport` via
`ThreadPoolExecutor`. With a `BatchPolicy(max_concurrency=4)`
attached:

- **Write-side calls (POST/PUT/PATCH/DELETE) are deferred** at queue
  time — the call dict gains `_deferred=True`, no immediate dispatch.
- **GET calls bypass deferral** — they remain synchronous so
  `get_file()` returns a populated `FileRef.last_modified` for
  concurrency detection and the agent runbook.
- **`commit_session()` flushes the batch** through the pool. Each
  worker runs its own `BackoffPolicy` retry schedule independently
  (the policy is pure arithmetic with no shared state, so this
  composes cleanly — 429 storms are jitter-distributed across
  threads, preventing thundering herd).
- **Best-effort failure semantics**: `_dispatch_one_safe()` wraps
  each per-call dispatch and records exceptions on the call dict's
  `error` key without raising. `SessionResult.operations_failed`
  counts failures; the batch always drains.

`SessionResult.artifacts` gained two diagnostic keys:
`batch_dispatched` (count of deferred calls flushed) and
`max_concurrency` (worker count). No dependency-graph machinery in
the policy — Figma's REST endpoints are server-versioned with
ETag/version semantics, so concurrent client writes are safe by the
server's guarantee. A client-side graph would double-book the
serialization Figma already provides.

Public API: 38 → 39 (`BatchPolicy`); `RestTransport.batch:
BatchPolicy | None = None` (default sequential — v1.x backward
compatible).

### 2.4 Mock server thread-safety (beta.1, test infrastructure)

`MockFigmaServer.request_log.append()` was bare; under concurrent
batch dispatch this raced. Added `_log_lock: threading.Lock` guarding
every append. Also added `set_response_sequence(method, path,
sequence)` for queueing ordered responses (e.g. 429-then-200) that
batch-with-backoff tests required.

This is test-fixture infrastructure, not part of the figma-forge
public API; recorded here for completeness because it enabled the
beta.1 acceptance tests.

## 3. Public API delta

The surface grew from 36 (v1.2.0) to 39 symbols (v1.3.0), all
additive; `API_VERSION` stays `"1.0"`:

| Symbol                  | Kind      | Milestone |
|-------------------------|-----------|-----------|
| `validate_mcp_plan`     | function  | alpha.1   |
| `PlanValidationReport`  | dataclass | alpha.1   |
| `BatchPolicy`           | dataclass | beta.1    |

Plus the internal `mcp_dispatch.REGISTRY` (alpha.2 — not exported on
`figma_forge.__all__`; intentionally unexposed because its contents
may change in any minor release as the Figma MCP write surface
matures).

- [x] `validate_mcp_plan` validates Düstur's real 265-step plan with
      0 schema errors, 0 argument errors, 0 ordering warnings; bad
      plans (envelope shape, step_count mismatch, mechanism
      violations, missing native args, non-monotonic step numbers)
      all surface as the right severity (alpha.1)
- [x] Validator's severity model documented in
      `references/walkthroughs/mcp-plan-execution.md`: strict on
      schema, soft on ordering; ordering warning text explicitly
      excluded from the stable contract (alpha.1)
- [x] Agent execution runbook documented: lifecycle, native vs
      use_figma_nl handling, idempotency, error recovery,
      post-step verification, `pytest -m live` convention (alpha.1)
- [x] `mcp_dispatch.REGISTRY` is the single source of truth; three
      consumer maps derived from it at import time
      (`_MCP_TOOL_FOR_OPERATION`, `_NATIVE_TOOL_REQUIRED_ARGS`,
      `CAPABILITY_MATRIX` MCP cells); consistency enforced by 12
      drift-prevention tests (alpha.2)
- [x] Promotion simulation test: temporarily overriding a registry
      entry propagates to all three consumers; restoration confirmed
      (alpha.2)
- [x] `BatchPolicy` opt-in (default `batch=None` preserves v1.x
      sequential behavior); writes deferred, GETs immediate;
      `enabled=False` acts like `None` (beta.1)
- [x] `BatchPolicy` + `BackoffPolicy` compose: per-thread independent
      retry schedules; 429-then-200 sequence verified via
      `set_response_sequence` mock helper (beta.1)
- [x] Failure semantics: per-call errors recorded on call dict,
      counted in `SessionResult.operations_failed`, batch drains all
      scheduled work (beta.1)
- [x] Full Düstur build (90 REST POSTs across `/v1/files/X/variables`
      + `/v1/code_connect`) completes through a 4-worker pool with
      no failures (beta.1)
- [x] Public API additive only; `API_VERSION` unchanged at `"1.0"`;
      all 39 symbols resolve; `api/STABILITY.md` finalized (GA)
- [x] No regression: 259 pytest + 8 verification gates = 267/267 (GA)
- [ ] **Live integration test against a real Figma file / live MCP
      host** — DEFERRED, as in v1.1 and v1.2. The sandbox has no
      egress to `api.figma.com`, no Enterprise PAT, and no live MCP
      Figma host. All dispatch and plan-emission paths are
      mock-verified; the operator executes against the real API /
      a real agent. The `pytest -m live` convention is documented
      in the v1.3.0-alpha.1 walkthrough.

**Status: 11 of 12 criteria MET. The 12th (live real-Figma /
real-MCP integration) is structurally impossible in the sandbox and
is delegated to the operator's environment — the infrastructure is
complete and mock-verified. v1.3.0 GA ships on this basis, consistent
with the v1.1.0 and v1.2.0 GA precedents.**

## 5. Risks & Open Questions

### 5.1 Risk: Figma MCP write surface evolution

The Figma MCP server's write tools may evolve unpredictably.
Operations currently marked `use_figma_nl` may gain native MCP tools;
existing native tools may change argument shapes. Mitigation: the
v1.3.0-alpha.2 registry makes promotion a one-line edit; the
v1.3.0-alpha.1 validator's native argument shape rules are documented
in STABILITY.md as **tracking** rather than contract (operators
pinning to specific behavior should pin a figma-forge version).

### 5.2 Risk: ThreadPoolExecutor thread-safety in operator code

`BatchPolicy` dispatches Figma POSTs in parallel through an internal
thread pool. If an operator's pipeline code mutates shared state in
the middle of a build (e.g. updating a registry from inside a
descriptor builder), races become possible. Mitigation: the pipeline
code path is purely descriptor-emit; no operator hook runs inside the
dispatch pool. The thread pool's worker function is
`_dispatch_one_safe`, which only touches its own call dict.

### 5.3 Open question: dependency graph for batch dispatch

`BatchPolicy` is concurrency control only, not ordering control —
trusting Figma's server-side versioning. If a future Figma endpoint
family loses transactional guarantees, a `preserve_order_groups`
field on `BatchPolicy` can be added additively. No commitment in
v1.3.

### 5.4 Open question: validator ordering precision

The ordering warning heuristic produces false positives on
cross-session plans. A future v1.4 could ingest "known-prior-state"
hints (e.g. a JSON of existing collection IDs) to suppress these.
For now warnings are documented as advisory.

## 6. Deferred beyond v1.3.0

- Promotion of specific `use_figma_nl` MCP operations to `native` as
  Figma ships the corresponding granular tools (one-line registry
  edits; non-breaking per the registry's design)
- Adaptive `max_concurrency` tuning based on observed rate-limit
  signals
- A reference agent-side plan executor (working code consuming
  `render_mcp_plan()` output and driving the Figma MCP tools);
  currently the validator + walkthrough specify the semantics
- Dependency graph for batch dispatch (only if Figma loses
  server-side serialization guarantees)
- Validator hints for cross-session plans (suppress ordering warnings
  when prior state is known)
