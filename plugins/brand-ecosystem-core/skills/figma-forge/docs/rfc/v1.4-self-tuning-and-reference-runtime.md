# RFC v1.4: Self-Tuning & Reference Runtime

> Status: **Accepted & Shipped** (v1.4.0 GA) · 2026-05-28
> Target sürüm: **v1.4.0** — shipped across alpha.1 → alpha.2 → beta.1 → GA
> Author: figma-forge maintainers
> Supersedes the v1.4 deferred items in RFC v1.3 §6

## 1. Motivation

RFC v1.3 closed the operational gaps in transport-layer dispatch:
plans could be validated before execution, the MCP dispatch registry
was a single source of truth, and REST batches dispatched in
parallel. The transport layer was now production-capable.

RFC v1.4 addresses a different category of gap — not what the
transport *can do*, but how operators and agents **consume** it
correctly. Three specific concerns surfaced from v1.3 production
usage:

1. **The plan validator was strict but session-naive.** A build
   targeting an existing library (build N+1 adding variables to
   collection ``vc_renkler`` created in build N) tripped the
   orphan-collection ordering warning, because the validator
   couldn't see what already existed in Figma. Operators
   suppressed the warning by inspection — a per-call manual step
   that didn't scale.
2. **Plan execution semantics were prose-only.** The
   ``references/walkthroughs/mcp-plan-execution.md`` §3 ("Agent
   runbook") was a careful prose specification of how an agent
   should walk a validated plan. But each agent re-implemented the
   loop from scratch, and the prose-to-code drift was visible
   across operators. The walkthrough was the source of truth; nine
   different agent loops were the result.
3. **REST concurrency was static.** ``BatchPolicy(max_concurrency=4)``
   was a guess. After a 90-call Düstur build, the operator had no
   structured signal whether 4 was too aggressive, too timid, or
   correct. Tuning required reading log timestamps and counting
   429s by hand.

This RFC records the design and acceptance of three features that
close these gaps. All three were designed to compose cleanly with
each other: ``PlanRunner.run(plan, validate=True, prior_state=...)``
exercises all three in a single call.

## 2. Features shipped

### 2.1 `PriorState` — cross-session validator hints (alpha.1)

A new frozen dataclass with four ``frozenset[str]`` hint fields:

```python
@dataclass(frozen=True)
class PriorState:
    known_collection_ids:   frozenset[str] = frozenset()
    known_collection_names: frozenset[str] = frozenset()
    known_component_names:  frozenset[str] = frozenset()
    known_page_names:       frozenset[str] = frozenset()
```

``validate_mcp_plan`` gained a keyword-only ``prior_state`` parameter
(default ``None``). When provided, the validator suppresses ordering
warnings for entities listed in the hint sets — strictly subtractive,
never additive. Schema and argument violations propagate unchanged;
``is_executable`` semantics are unaffected.

Three sourcing patterns are documented in the walkthrough (§2):
prior-build audit trail (``mcp_cursor`` writer log replay), live
Figma query, and bundle manifest. All three preserve the same
``PriorState`` contract — the hint sets are content-addressed by
name/ID, so any source that can produce them is interchangeable.

### 2.2 `PlanRunner` — reference plan executor (alpha.2)

The canonical execution semantics of walkthrough §3, expressed as
working code. ``PlanRunner`` walks a plan envelope step-by-step and
invokes injectable ``native_dispatch(mcp_tool, args)`` and
``nl_dispatch(instruction, args)`` callables. Default no-op
dispatchers make a bare ``PlanRunner()`` a useful dry-run validator
— verifies schema and walks all 265 Düstur steps without side
effects.

Three new public symbols ship together:

- ``PlanRunner`` — the runner class with constructor parameters
  ``native_dispatch``, ``nl_dispatch``, ``on_step``,
  ``abort_on_failure``, and a ``run(plan, *, validate=True,
  prior_state=None)`` method that composes the v1.3 validator + v1.4
  ``PriorState`` hints + the execution loop into one call.
- ``PlanRunResult`` — aggregate outcome with counters, per-step
  results, ``aborted_on_step``, ``validation_report``, and an
  ``is_success`` property that captures operator intent (true only
  when zero failures, no abort, and plan was executable).
- ``StepResult`` — frozen per-step outcome with ``status``,
  ``response``, ``error``, ``duration_ms``.

The walkthrough §3 was rewritten to open with a ``PlanRunner`` usage
block and an explicit drift-resolution note: *"the prose remains as
the readable specification; the runner is the normative executable
form. If the two ever drift, the runner wins."* This collapses the
nine-loop problem into a single shared reference.

The runner deliberately does **not** implement retries — per-step
retry policy belongs to the dispatch callables (the same boundary
``BackoffPolicy`` sits at in v1.2/v1.3). The runner inherits whatever
retry semantics the operator's MCP host provides.

### 2.3 `AdaptiveConcurrency` — observed-rate-limit-driven recommendations (beta.1)

A frozen dataclass policy that attaches to ``BatchPolicy.adaptive``
and turns batch-dispatch rate-limit telemetry into a recommendation
for the next build's ``max_concurrency``:

```python
@dataclass(frozen=True)
class AdaptiveConcurrency:
    min_concurrency:     int   = 1
    max_concurrency:     int   = 16
    target_429_ratio:    float = 0.05
    aggressive_scale_up: bool  = False
    min_sample_size:     int   = 10
```

After each batch dispatch, ``RestTransport`` aggregates per-call
telemetry under a ``threading.Lock`` (``requests_total`` including
retries, ``requests_429``, ``requests_5xx``,
``retry_after_seconds_max``) and produces a
``ConcurrencyObservation`` containing the recommendation and a
human-readable rationale. The observation is attached to a new
optional field ``SessionResult.adaptive_observation``
(default ``None`` for backward compatibility).

The algorithm:

| Condition | Action |
|---|---|
| ``requests_total < min_sample_size`` | hold |
| ``r > target_429_ratio`` | scale down 1 (capped at min) |
| ``r == 0`` | scale up 1 (or 2 if ``aggressive_scale_up``) |
| ``0 < r ≤ target_429_ratio`` | hold |

**Recommendation, not self-tuning** — the design's most important
property. The running policy is never mutated mid-batch. The
operator inspects ``SessionResult.adaptive_observation`` after the
build, decides whether to apply, and rebuilds ``BatchPolicy`` for
the next build. This keeps control with the operator and prevents
noisy single-batch observations from ratcheting concurrency into
degenerate states.

5xx errors are tracked separately from 429s because they have
different causes (server-side fault vs client over-pressure) and
warrant different responses (hold or scale up vs scale down).
Operators see ``requests_5xx`` in the observation as a Figma-health
signal independent of their own concurrency choice.

### 2.4 Compositional design

All three features compose into a single call:

```python
runner = ff.PlanRunner(
    native_dispatch=lambda tool, args: my_mcp.call(tool, args),
    nl_dispatch=lambda instr, args: my_mcp.call("Figma:use_figma", {"instruction": instr}),
)
result = runner.run(
    plan,                                    # v1.3.0-alpha.1 (validate_mcp_plan)
    validate=True,                           # gate before dispatch
    prior_state=ff.PriorState(               # v1.4.0-alpha.1 (cross-session hints)
        known_collection_ids=frozenset({"vc_renkler"}),
    ),
    # → v1.4.0-alpha.2: PlanRunner walks the validated, hint-suppressed plan
)
# Separately, on the REST side:
rest = ff.RestTransport(..., batch=ff.BatchPolicy(
    max_concurrency=4,
    adaptive=ff.AdaptiveConcurrency(min_concurrency=1, max_concurrency=8),
))
# After commit_session, rest.session_results["..."].adaptive_observation
# carries the v1.4.0-beta.1 recommendation for the next build.
```

This is the v1.4 acceptance test in its smallest form.

## 3. Public API delta

The v1.4.0 line added **6 symbols** (39 → 45) — all append-only.
``API_VERSION`` remains ``"1.0"`` because the v1.x contract is
unchanged by additive minor releases.

| Symbol | Kind | Module | Sürüm |
|---|---|---|---|
| ``PriorState`` | dataclass (frozen) | ``transport.plan_validation`` | v1.4.0-alpha.1 |
| ``PlanRunner`` | class | ``transport.plan_runner`` | v1.4.0-alpha.2 |
| ``PlanRunResult`` | dataclass | ``transport.plan_runner`` | v1.4.0-alpha.2 |
| ``StepResult`` | dataclass (frozen) | ``transport.plan_runner`` | v1.4.0-alpha.2 |
| ``AdaptiveConcurrency`` | dataclass (frozen) | ``transport.adaptive_concurrency`` | v1.4.0-beta.1 |
| ``ConcurrencyObservation`` | dataclass (frozen) | ``transport.adaptive_concurrency`` | v1.4.0-beta.1 |

In addition:

- ``validate_mcp_plan`` gained a keyword-only ``prior_state``
  parameter (default ``None`` — v1.3 callers unaffected).
- ``BatchPolicy`` gained an optional ``adaptive`` field
  (default ``None`` — v1.3 callers unaffected).
- ``SessionResult`` gained an optional ``adaptive_observation``
  field (default ``None`` — all v1.3 adapters and test fixtures
  unaffected; verified by 289 pre-existing tests passing unchanged
  after the field was added).

## 5. Risks & Open Questions

### 5.1 Risk: ``PriorState`` staleness

A ``PriorState`` built from a prior build may be stale by the time
the next build runs (someone else edited the file in between).
v1.4.0-alpha.1 mitigates this only partially: stale hints can cause
the validator to suppress a warning that *would* have been correct
(the collection no longer exists). The current contract is that
``PriorState`` is operator-supplied and the operator owns its
freshness.

**Mitigation path:** v1.5 may add a ``last_verified_at`` field to
``PriorState`` and a freshness-window warning. Not in scope for v1.4.

### 5.2 Risk: ``PlanRunner`` and concurrency

``PlanRunner`` is currently sequential — it walks the plan
step-by-step. The plan validator enforces an ordering invariant
(collection creation before variable creation, etc.) that makes
sequential dispatch the safest default. Operators who want
concurrent dispatch within a plan must implement it inside their
``native_dispatch`` / ``nl_dispatch`` callables (e.g., by batching
operationally-independent steps).

**Mitigation path:** v1.5 may add a plan-aware concurrency layer
that uses the validator's dependency information to identify
parallelizable step clusters. Not in scope for v1.4.

### 5.3 Risk: ``AdaptiveConcurrency`` single-batch noise

A single batch with an unrepresentative 429 ratio can produce a
recommendation that, applied directly, ratchets concurrency into a
degenerate state. The v1.4 design defends against this by
*recommending* rather than *applying* — the operator is the
required smoothing layer. But if an operator scripts blind
application of every recommendation, they reintroduce the failure
mode.

**Mitigation path:** v1.5 may add a multi-batch smoothing policy
(``AdaptiveConcurrency(window=5)``) that requires N consecutive
observations agreeing on direction before recommending a change.
Not in scope for v1.4.

### 5.4 Open question: ``PlanRunner`` and retry telemetry

``PlanRunner`` does not retry — the dispatch callable does. But
when the callable retries internally, the runner's ``StepResult``
has no insight into the retry count or per-retry delays. For pure
``PlanRunner`` execution, this is correct (separation of concerns).
But for combined ``PlanRunner`` + ``RestTransport`` execution, an
operator may want to see retry telemetry in the runner's output.

**Mitigation path:** the dispatch callable can return a richer
response object (e.g., ``{"id": ..., "retry_attempts": 2}``) and
the runner will capture it in ``StepResult.response`` — no API
change needed. v1.5 may standardize a ``DispatchResponse`` type.
Not in scope for v1.4.

### 5.5 Open question: ``ConcurrencyObservation`` cross-build durability

``ConcurrencyObservation`` is attached to a single
``SessionResult``. If the operator wants to track concurrency
trend across many builds, they have to harvest and persist the
observations themselves. v1.4 doesn't ship a built-in persistence
layer.

**Mitigation path:** v1.5 may add an ``ObservationLog`` that
operators can attach to ``RestTransport`` for automatic
accumulation. Not in scope for v1.4.

## 6. Deferred beyond v1.4.0

The following items were considered for v1.4 and explicitly
deferred to keep scope tight:

- **Multi-batch smoothing window for ``AdaptiveConcurrency``** (5.3
  mitigation). Pushed to v1.5; current single-batch recommendation
  is sufficient with operator review.
- **``PriorState`` staleness handling** (5.1 mitigation). Pushed to
  v1.5; operator owns freshness in v1.4.
- **Plan-aware concurrent ``PlanRunner``** (5.2 mitigation). Pushed
  to v1.5; sequential dispatch is the safe default.
- **``DispatchResponse`` standardized type** (5.4 mitigation).
  Pushed to v1.5; opaque response is sufficient for v1.4.
- **``ObservationLog`` cross-build persistence** (5.5 mitigation).
  Pushed to v1.5; operator owns persistence in v1.4.
- **Live-Figma integration test** (acceptance criterion 19).
  Continues the v1.1 / v1.2 / v1.3 deferral pattern; operator
  pilot will close this independently.
