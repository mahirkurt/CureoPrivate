# RFC v1.5: Durability & Smoothing

> Status: **Accepted & Shipped** (v1.5.0 GA) · 2026-05-28
> Target sürüm: **v1.5.0** — shipped across alpha.1 → alpha.2 → beta.1 → GA
> Author: figma-forge maintainers
> Supersedes the v1.5 deferred items in RFC v1.4 §6

## 1. Motivation

RFC v1.4 closed the consumption gaps in the transport layer: plans
could be executed by a reference runner, the validator could be
seeded with cross-session hints, and batch concurrency produced a
recommendation. Three of the five risks enumerated in RFC v1.4 §5
were explicitly deferred to v1.5 as "mitigation paths" — they were
known weaknesses in the v1.4 features, not new capabilities.

RFC v1.5 addresses those three deferred mitigations. Each one
hardens an existing v1.4 feature rather than introducing a new
capability axis:

1. **`PriorState` could go stale silently** (RFC v1.4 §5.1). A hint
   set built from a prior build may no longer reflect live Figma
   state by the time the next build runs. A stale hint causes the
   validator to suppress a warning that *should* have fired (the
   collection no longer exists). v1.4 left freshness entirely to
   the operator with no machinery to detect staleness.
2. **`AdaptiveConcurrency` reacted to single-batch noise** (RFC v1.4
   §5.3). One batch with an unrepresentative 429 ratio could drive
   a recommendation that, applied blindly, ratchets concurrency
   into a degenerate state. v1.4's defense was "recommendation, not
   self-tuning" — the operator was the only smoothing layer.
3. **Smoothing history was instance-bound** (RFC v1.4 §5.5). Even
   after v1.5.0-alpha.2 added a multi-batch window, the history
   lived in a transport instance attribute and evaporated at
   process exit — so the common CI/CD pattern (each build a fresh
   process issuing one batch) never accumulated more than one
   observation, rendering smoothing inert exactly where it was most
   wanted.

This RFC records the design and acceptance of the three features
that close these gaps. Notably, two of the three required **zero new
public symbols** — they extended existing dataclasses with
append-only fields and methods — reflecting a deliberate "spec
minimalism" discipline: add a symbol only where a genuinely new
object is required (here, only `ObservationLog`, whose file-backed
nature demands an object).

## 2. Features shipped

### 2.1 `PriorState.last_verified_at` + freshness check (alpha.1)

`PriorState` gained an optional timezone-aware `last_verified_at`
datetime recording when the hint set was last reconciled with live
Figma state. `validate_mcp_plan` gained a keyword-only
`freshness_window_seconds` parameter; when both are set, hints older
than the window contribute to a new `PlanValidationReport.freshness_warnings`
list.

Three deliberate semantic choices:

- **Naive datetimes are rejected at construction** with `ValueError`.
  A hint with no timezone is ambiguous about which clock it refers
  to, and silently treating it as UTC can mask staleness across a
  team operating in multiple zones. The error surfaces at the
  `PriorState(...)` call site, not deep inside the validator.
- **Freshness warnings never block execution.** `is_executable`
  remains determined solely by schema and argument errors. An
  operator may legitimately validate offline with stale hints when
  live reconciliation is unavailable (CI without MCP credentials,
  air-gapped build). Treating staleness as a hard error would force
  one of two failure modes: skip the freshness check (defeating the
  purpose) or block legitimate offline builds (defeating the
  workflow).
- **Clock skew is distinguished.** A `last_verified_at` in the
  future produces a separate warning identifying the skew direction
  and magnitude.

`PlanRunner.run` forwards `freshness_window_seconds` to the
validator, so the check applies in the runner path too. **Zero new
public symbols** — append-only field + append-only field + keyword
parameter.

### 2.2 `AdaptiveConcurrency.window` + `recommend_aggregate` (alpha.2)

`AdaptiveConcurrency` gained an optional `window: int = 1` field
(default = exactly v1.4 behavior) and a `recommend_aggregate(current,
observations)` method that sums `requests_total` and `requests_429`
across a window of observations and feeds the aggregate through the
existing `recommend()`. `RestTransport` accumulates the last `window`
observations in a bounded `collections.deque(maxlen=window)`.

The smoothing strategy is **aggregate ratio over standalone
counters**, chosen over majority-direction, median-ratio, and
latest-N-consistent for three reasons:

1. **Statistical strength** — aggregate sample sizes (e.g. 5 batches
   × 50 requests = 250 requests) reduce noise variance proportional
   to √N. A single batch's 1/3 spike becomes a 1/103 contribution to
   the aggregate.
2. **Single code path** — reuses `recommend()` without divergence.
   Window=1 → deque size 1 → aggregate = the single latest
   observation → exactly v1.4 behavior. No special case for the
   common path.
3. **`min_sample_size` consistency** — the threshold applies to the
   aggregate, so several small batches can collectively pass a
   threshold none of them would individually.

Crucially, aggregation **dilutes noise without masking sustained
pressure**: a single spike in a 5-batch window is diluted to "hold",
but five consecutive 20%-429 batches still aggregate to 20% and
recommend "scale down". Aggregation preserves the mean and reduces
the variance. **Zero new public symbols** — append-only field +
method.

### 2.3 `ObservationLog` cross-build persistence (beta.1)

`ObservationLog` is a file-backed JSONL append log for
`ConcurrencyObservation` records. `RestTransport` gained an optional
`observation_log` field: at construction it seeds `_observation_history`
from the log's recent records; on `commit_session` it appends the
new observation. Smoothing then spans process boundaries — build N+1
sees builds N, N-1, … N-window+1.

Durability properties:

- **Append under an exclusive file lock** (`fcntl.flock` POSIX,
  `msvcrt.locking` Windows, best-effort no-op elsewhere) so
  concurrent processes don't interleave partial lines.
- **Amortized atomic trim** — when the file grows past
  `max_records × 2`, it's rewritten to the last `max_records` lines
  via temp file + `os.replace`. Amortized O(1) per append; a crash
  during trim leaves either the old file intact or the new file
  complete, never a partial.
- **Corrupted-record tolerance** — a line that fails to parse is
  skipped on read, never raising. A crash mid-write costs at most
  one observation.

The on-disk wrapper format `{"logged_at": ..., "observation": {...}}`
keeps the log's metadata separate from observation fields, so the
v1.4 `ConcurrencyObservation` dataclass is unchanged. The reader
accepts both wrapper and bare-dict forms, filters unknown keys
(forward compatibility), and rejects records missing required
fields. **+1 public symbol** (`ObservationLog`) — the only new
symbol in the entire v1.5 line.

### 2.4 Compositional design

The three features stack into the CI/CD pattern that motivated the
whole line:

```python
log = ff.ObservationLog(".figma-forge/history.jsonl", max_records=50)
rest = ff.RestTransport(
    pat=os.environ["FIGMA_PAT"],
    batch=ff.BatchPolicy(
        max_concurrency=int(os.environ.get("FF_CONCURRENCY", "4")),
        adaptive=ff.AdaptiveConcurrency(window=5),  # alpha.2 smoothing
    ),
    observation_log=log,                            # beta.1 persistence
)
# Each build seeds from the log, appends its observation, and the
# window fills across builds even though each is a fresh process.

# Orthogonally, the validator's freshness check (alpha.1):
report = ff.validate_mcp_plan(
    plan,
    prior_state=ff.PriorState(..., last_verified_at=last_seen),
    freshness_window_seconds=300,
)
```

This is the v1.5 acceptance test in its smallest practical form.

The v1.5.0 line added **1 symbol** (45 → 46) — `ObservationLog`. The
other two features are field-/method-level extensions. `API_VERSION`
remains `"1.0"` because the v1.x contract is unchanged by additive
minor releases.

Backward-compatibility verifications (each milestone re-ran the full
prior suite unchanged):

- `PriorState()` with no `last_verified_at` → exact v1.4 behavior;
  308 v1.4 tests passed unchanged after the field was added.

  behavior; 322 alpha.1 tests passed unchanged.
- `RestTransport(...)` with no `observation_log` → exact alpha.2
  behavior; 338 alpha.2 tests passed unchanged.

## 5. Risks & Open Questions

### 5.1 Risk: `ObservationLog` unbounded path growth in pathological cases

The amortized trim keeps the file near `max_records × 2` under
normal append patterns. But a process that crashes repeatedly
between the append and the trim check could, in theory, leave the
file slightly larger than `2 × max_records`. In practice the trim
runs on the *next* successful append, so the overage is transient.

**Mitigation path:** v1.6 may add an explicit `compact()` method
and/or a trim-on-read option. Not in scope for v1.5 — the transient
overage is bounded and self-correcting.

### 5.2 Risk: `ObservationLog` concurrent-write correctness on network filesystems

`fcntl.flock` semantics are unreliable on some network filesystems
(NFS without lockd, certain SMB configurations). The log's
corrupted-record tolerance on read defends against interleaved
writes, but two processes appending simultaneously on a flock-broken
filesystem could still lose records.

**Mitigation path:** v1.6 may add an optional per-process file
(`history.{pid}.jsonl`) with read-time merge, eliminating the shared
write path. Not in scope for v1.5 — local filesystems (the common CI
case) honor flock correctly.

### 5.3 Open question: freshness check granularity

`freshness_window_seconds` applies one TTL to the entire hint set.
But different entity classes age at different rates — collection IDs
are more stable than component names. A single TTL is a coarse
approximation.

**Mitigation path:** v1.6 may add per-field TTLs
(`freshness_window_seconds={"collection_ids": 3600, "component_names": 300}`).
Not in scope for v1.5 — a single TTL covers the dominant use case.

### 5.4 Open question: smoothing window vs. responsiveness trade-off

A larger `window` smooths more aggressively but responds more slowly
to genuine sustained changes — it takes up to `window` batches to
fully react. There's no built-in guidance on choosing the window
size for a given workload.

**Mitigation path:** v1.6 may add a heuristic
`AdaptiveConcurrency.suggest_window(observed_variance)` helper. Not
in scope for v1.5 — the operator chooses based on their batch
cadence.

## 6. Deferred beyond v1.5.0

The following items were considered and deferred to keep scope
tight. The first two are the remaining large items from RFC v1.4 §6;
the rest are v1.5-specific:

- **`DispatchResponse` standardized type** (from RFC v1.4 §5.4) —
  formalize the opaque response contract between `PlanRunner` and
  its dispatch callables. Pushed to v1.6; opaque response is
  sufficient for v1.5.
- **Plan-aware concurrent `PlanRunner`** (from RFC v1.4 §5.2) — use
  the validator's dependency information to identify parallelizable
  step clusters. The largest remaining item; pushed to v1.6 and
  likely to warrant its own RFC. Sequential dispatch remains the
  safe default.
- **`ObservationLog.compact()` + per-process files** (5.1, 5.2
  mitigations). Pushed to v1.6.
- **Per-field freshness TTLs** (5.3 mitigation). Pushed to v1.6.
- **`suggest_window` heuristic** (5.4 mitigation). Pushed to v1.6.
- **Live-Figma integration test** (acceptance criterion 20).
  Continues the v1.1 / v1.2 / v1.3 / v1.4 deferral pattern; operator
  pilot will close this independently.
