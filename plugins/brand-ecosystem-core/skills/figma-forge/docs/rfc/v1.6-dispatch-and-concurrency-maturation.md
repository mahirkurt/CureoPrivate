# RFC v1.6: Dispatch & Concurrency Maturation

- **Status:** Accepted & Shipped
- **Line:** v1.6.0 (alpha.1 → alpha.2 → beta.1 → GA)
- **Supersedes deferrals from:** RFC v1.4 §6 (DispatchResponse, concurrent PlanRunner) and RFC v1.5 §6 (compact, per-field TTL, suggest_window)
- **Public API:** 46 → 48 symbols (+2: `DispatchResponse`, `plan_execution_layers`); `API_VERSION` unchanged at `"1.0"`

## 1. Motivation

v1.6 is **the closure release**. Where v1.4 introduced the reference
runtime (`PlanRunner`) and v1.5 hardened the transport's durability
mechanisms, neither line closed its own deferral list. RFC v1.4 §6
left two large items unbuilt — a standardized dispatch-return type
and a concurrent execution model — explicitly because each deserved
its own design pass. RFC v1.5 §6 then carried those two forward and
added three of its own mitigations (on-demand log compaction,
per-entity-class freshness TTLs, an automatic window-size
suggestion).

v1.6 discharges all five. There is no new theme to introduce; the
theme is *finishing*. Concretely, the line answers three questions
the reference runtime had left open:

1. **How does a dispatch callable report richer outcomes?** v1.4's
   `PlanRunner` captured whatever a callable returned as an opaque
   `StepResult.response`. There was no way to signal a *soft*
   failure (the MCP host returned 2xx but the operation was
   logically unsuccessful), surface retry telemetry, or stash a
   created entity ID without parsing the raw blob. → **alpha.1:
   `DispatchResponse`.**

2. **Can the runner exploit the dependency graph it already
   computes?** The validator (v1.1+) knew which steps depended on
   which, but that information drove only ordering *warnings*. The
   runner walked every plan sequentially even when half its steps
   were mutually independent. → **alpha.2: plan-aware concurrent
   execution.**

3. **Do the v1.4/v1.5 durability mechanisms have operational
   sharp edges?** Three: the observation log could only be trimmed
   amortized-during-append (no operator-triggered reclaim); freshness
   used one window for entity classes that age at very different
   rates; and the smoothing window was a hand-tuned integer with no
   guidance. → **beta.1: `compact()`, per-class freshness TTLs,
   `suggest_window`.**

The discipline across all three milestones is the one established in
v1.5: **a maturation line should not inflate the public surface
beyond what genuinely new objects require.** alpha.1 and alpha.2 each
introduce exactly one new symbol (a new return *object* and a new
graph-layering *function* — both irreducible); beta.1 introduces
zero, attaching all three features as methods and keyword parameters
to existing objects.

## 2. Features shipped

### 2.1 `DispatchResponse` standardized type (alpha.1)

A frozen, opt-in dataclass a `PlanRunner` dispatch callable *may*
return:

```python
@dataclass(frozen=True)
class DispatchResponse:
    ok: bool = True
    entity_id: str | None = None
    raw: Any = None
    retry_attempts: int = 0
    warnings: tuple[str, ...] = ()
```

The central design decision is **two unified failure channels**. A
dispatch callable can now signal failure two ways, both of which
mark the step `"failure"` and trigger `abort_on_failure`:

1. **Raise an exception** — a hard failure (`repr(exc)` →
   `StepResult.error`), the v1.4 behavior.
2. **Return `DispatchResponse(ok=False)`** — a soft failure, for
   when the host returned 2xx but the operation was logically
   unsuccessful (name collision, entity-already-exists, validation
   rejection). The `warnings` become the `error` string.

`StepResult` gained an append-only `dispatch_response` field (typed
accessor; `None` when the callable returned anything else). **A
non-`DispatchResponse` return is always treated as success** — the
runner never inspects opaque returns for failure signals, so every
v1.5 dispatch callable keeps working unchanged.

### 2.2 Plan-aware concurrent execution (alpha.2)

Two additions. First, a new public function:

```python
def plan_execution_layers(plan) -> list[list[int]]: ...
```

It computes a Kahn-style longest-path topological layering of the
plan's steps using the **validator's exact producer/consumer
dependency model** (collection→variable, page→component,
component→instance). Each inner list is a set of steps with no
inter-dependencies; the outer list orders the layers so every step's
dependencies complete earlier. It is cycle-tolerant (a malformed
plan degrades to singleton layers in plan order rather than raising)
and preserves plan order within each layer.

Second, `PlanRunner.run` gained two append-only keyword parameters:

```python
def run(self, plan, *, validate=True, prior_state=None,
        freshness_window_seconds=None, freshness_window_overrides=None,
        concurrent=False, max_workers=4): ...
```

With `concurrent=True`, each layer's steps are dispatched across a
`ThreadPoolExecutor`, layers in order. **Three guarantees:**

1. **Same dependency model as the validator** — a reference with no
   in-plan producer imposes no ordering (satisfied by prior state).
2. **Deterministic, plan-ordered output** — `step_results` is always
   assembled in ascending step order regardless of completion order,
   and `on_step` fires in plan order. A concurrent run is
   output-indistinguishable from a sequential one, only faster.
3. **Layer-granular abort** — with `abort_on_failure=True`, a
   failure lets its layer complete (steps already in flight finish),
   then later layers are skipped; `aborted_on_step` is the
   lowest-numbered failing step in the triggering layer.

A shared `_execute_step` helper backs both the sequential and
concurrent paths, guaranteeing identical `StepResult` semantics
(including `DispatchResponse` recognition). Singleton layers run
inline (no thread-pool overhead); only wider layers fan out.

### 2.3 Three cleanup mitigations (beta.1)

**`ObservationLog.compact(keep=None)`** — the operator-triggered
counterpart to the automatic amortized trim. Runs unconditionally
(the amortized trim only fires past `max_records × 2` during
append), drops corrupted/blank lines *and* overflow records, is
atomic under the same exclusive lock as `append`, returns the number
of lines removed, performs no rewrite when already clean and within
budget, and raises `ValueError` for `keep < 1` (use `clear()` to
drop all).

**Per-entity-class freshness TTLs** —
`validate_mcp_plan(..., freshness_window_overrides={"collection":
3600, "component": 300})` gives each class its own staleness window
(`freshness_window_seconds` is the fallback). A class is evaluated
only if it has a hint; clock skew stays class-independent. **Scalar
mode (`overrides=None`) is byte-for-byte the v1.5.0-alpha.1
behavior.** `PlanRunner.run` forwards the parameter.

**`AdaptiveConcurrency.suggest_window(observations,
max_suggested=10)`** — a recommendation (never mutates the frozen
`window` field) combining two orthogonal signals and taking the
larger: sample sufficiency (`ceil(min_sample_size /
avg_batch_total)`) and 429-ratio volatility (coefficient of
variation), clamped to `[1, max_suggested]`.

### 2.4 Compositional design

The three milestones interlock without coupling:

```python
# alpha.1 + alpha.2: structured returns in a concurrent run.
def dispatch(mcp_tool, args):
    resp = host.call(mcp_tool, args)
    return ff.DispatchResponse(ok=resp.ok, entity_id=resp.node_id,
                               retry_attempts=resp.attempts)

result = ff.PlanRunner(native_dispatch=dispatch, abort_on_failure=True).run(
    plan, concurrent=True, max_workers=8,
    freshness_window_overrides={"collection": 3600},  # beta.1
)
# Layers parallelize independent steps; each StepResult carries a
# typed dispatch_response; a soft failure aborts at layer
# granularity; stale-collection hints would warn (advisory only).

# beta.1: close the CI loop on the observation log.
log = ff.ObservationLog("history.jsonl", max_records=200)
removed = log.compact()                                 # reclaim on exit
window, why = ff.AdaptiveConcurrency().suggest_window(log.read_recent())
```

Each feature is independently testable and independently optional;
together they complete the runtime's dispatch, concurrency, and
durability stories.

## 5. Risks & Open Questions

### 5.1 Risk: thread-safety of dispatch callables under `concurrent=True`

The runner guarantees its own bookkeeping is correct (results are
collected per-future and assembled single-threaded), but it cannot
guarantee the operator's dispatch callable is thread-safe. A
callable that mutates shared state without synchronization, or an
MCP host client that is not safe for concurrent use, will misbehave
under `concurrent=True`. **Mitigation:** documented prominently;
`concurrent=False` remains the default; `max_workers=1` offers a
middle ground (layered structure, serialized dispatch). The runner
does not — and should not — attempt to lock the operator's code.

### 5.2 Risk: `ThreadPoolExecutor` and the GIL for CPU-bound dispatch

The concurrency model assumes dispatch is **I/O-bound** (network
round-trips to an MCP host), where threads genuinely overlap. A
CPU-bound dispatch callable would see little speedup under the GIL.
**Mitigation:** this is the correct assumption for the use case —
every dispatch is a Figma MCP call — and the wall-clock probe
confirms real overlap for sleeping (I/O-surrogate) dispatch. A
process-pool variant was considered and rejected: it would force
dispatch callables and their returns to be picklable, a heavy
constraint for a speedup the use case does not need.

### 5.3 Open question: per-class freshness for variable IDs vs. names

The per-class TTL model (beta.1) treats `collection` as one class,
covering both `known_collection_ids` and `known_collection_names`.
In principle an ID (stable) and a name (mutable) within the same
class could warrant different TTLs. This was judged over-fine for
v1.6 — the three-class granularity already captures the dominant
distinction (collections age slower than components). A future minor
release could split ID-vs-name if operators report a need.

### 5.4 Open question: `suggest_window` heuristic weighting

`suggest_window` takes the *larger* of the sample-sufficiency and
volatility terms. An alternative — a weighted blend — was
considered. "Larger of two" was chosen for interpretability: the
rationale string can name a single dominant signal, and the operator
can reason about each term independently. The stability contract
(§4 of `api/STABILITY.md`) commits only to the clamp range and
purity, leaving the exact weighting free to evolve.

## 6. Deferred beyond v1.6.0

With the v1.4 deferral list now fully discharged, only smaller items
remain:

- **Per-process `ObservationLog` files** (the second half of RFC
  v1.5 §5.2) — sharding the log per process to sidestep network-FS
  lock contention entirely. `compact()` and the exclusive-lock model
  cover the common case; per-process sharding is a scale-out
  refinement for high-fan-out CI, deferred until an operator hits the
  contention ceiling.
- **ID-vs-name freshness split** (§5.3 above).
- **Process-pool concurrency variant** (§5.2 above) — rejected for
  v1.6, revisitable only if a CPU-bound dispatch use case emerges.
- **Live-Figma integration test** (acceptance criterion 22).
  Continues the v1.1–v1.5 deferral pattern; operator pilot will close
  this independently.
