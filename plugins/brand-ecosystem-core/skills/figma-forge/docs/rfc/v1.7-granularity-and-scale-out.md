## 1. Motivation

v1.6 was the closure release: it discharged the entire v1.4 deferral
list and the v1.5 mitigation list. What remains in RFC v1.6 §6 is a
short tail of *smaller* items, two of which are genuine engineering
work:

1. **Per-process `ObservationLog` files** (the second half of RFC
   v1.5 §5.2) — sharding the observation log per process so that
   high-fan-out CI sidesteps network-filesystem lock contention
   entirely.
2. **ID-vs-name freshness split** (RFC v1.6 §5.3) — letting a
   collection's stable *ID* and its mutable *name* carry different
   freshness TTLs, rather than sharing the single `"collection"`
   class introduced in v1.6.0-beta.1.

These two items share a theme that is neither "new capability" nor
"hardening": they both **increase the granularity** of a v1.5/v1.6
mechanism. Sharding refines the observation log's *physical*
granularity (one file → one file per writer); the freshness split
refines the validator's *logical* granularity (one class → ID and
name sub-classes). The line is therefore named **Granularity &
Scale-Out**.

The remaining v1.6 §6 items are explicitly **not** in scope and are
re-affirmed as rejected/deferred in §6 below: the process-pool
concurrency variant (no CPU-bound dispatch use case has emerged) and
the live-Figma integration test (operator pilot territory — the test
environment has no network).

### Why now, and why small

v1.6 closed the large-feature backlog. The honest assessment is that
v1.7 is a **small, optional line**: neither feature is forced by a
known operator failure. Sharding matters only above a fan-out
ceiling no Düstur build has hit; the freshness split matters only to
operators who have adopted per-class TTLs *and* want finer control.
This RFC therefore also serves as a **decision point**: it lays out
the work precisely enough that the line can be greenlit, deferred, or
declined on its merits, rather than built on momentum. (See §8 for
the explicit "should we build this at all?" framing.)

## 2. Theme: Granularity & Scale-Out

| Mechanism (origin) | Current granularity | v1.7 proposed granularity |
|---|---|---|
| `ObservationLog` (v1.5.0-beta.1) | one file, exclusive-locked | one file *per process*, lock-free writes, merged reads |
| Per-class freshness TTLs (v1.6.0-beta.1) | 3 classes: `collection` / `component` / `page` | `collection` splits into `collection_id` / `collection_name` (4 effective keys + the `collection` alias) |

The design constraint inherited from v1.5/v1.6 holds: **append-only,
backward-compatible, and a maturation line should not inflate the
public surface beyond what genuinely new objects require.** Both
features are *intended* to land at +0 symbols (§5.1 documents the
single open question that could force a +1).

## 3. Proposed scope

**In scope:**

- Per-process sharded mode for `ObservationLog` (lock-free writes,
  merged reads, per-shard compaction, dead-shard reaping).
- ID-vs-name split for per-class freshness TTLs, with the existing
  `"collection"` key preserved as a both-cover alias.
- Supporting read/merge ergonomics required by sharding (a
  deterministic cross-shard merge by `logged_at`).

**Out of scope (see §6):**

- Process-pool concurrency variant (re-affirmed rejected).
- Live-Figma integration test (re-affirmed operator pilot).
- Any change to the *semantics* of an existing symbol — v1.7 is
  purely additive, like every minor release since v1.0.0.

## 4. Proposed features

### 4.1 Per-process `ObservationLog` sharding (proposed: alpha.1)

**Problem.** The v1.5/v1.6 log is a single file guarded by an
`fcntl`/`msvcrt` exclusive lock. On a local filesystem this is
correct and cheap. On a *network* filesystem (NFS, SMB) — the
high-fan-out CI case — advisory locks are unreliable or slow, and
many concurrent CI workers appending to one shared log can serialize
on the lock or, worse, interleave partial writes if the lock is not
honored.

**Proposed design.** Add an opt-in sharded mode where **each writer
owns its own file** and never contends:

```python
# Proposed — exact surface pending §5.1.
log = ff.ObservationLog(
    "history.jsonl",
    max_records=200,
    shard_per_process=True,   # NEW, default False (current behavior)
)
log.append(obs)               # writes to history.<shard-id>.jsonl — NO LOCK
recent = log.read_recent(50)  # globs history.*.jsonl, merges by logged_at
```

- **Shard identity.** A shard ID must be unique per concurrent
  writer and stable for that writer's lifetime. *(open, §5.2)* —
  candidate: `f"{os.getpid()}-{_host_token()}"` where `_host_token`
  is a short stable hash of the hostname (pid alone collides across
  hosts sharing a network mount). A start-time component may be
  needed to disambiguate pid reuse.
- **Append is lock-free.** Each process appends only to its own
  shard, so the exclusive lock — the entire source of contention —
  is removed in sharded mode. This is the whole point of the
  feature.
- **Read merges shards.** `read_recent` globs the shard set, parses
  each (tolerating corruption as today), and merges by the
  `logged_at` wrapper timestamp into a single oldest-first stream,
  returning the last `n`. The merge is deterministic given the
  timestamps.
- **Compaction is per-shard.** `compact()` compacts each shard
  independently under that shard's own (uncontended) write.
  Dead-shard reaping *(open, §5.3)* — shards from exited processes
  accumulate; a reaping policy (age-based? a liveness probe?) is
  needed so the shard set does not grow without bound.
- **Backward compatibility.** `shard_per_process=False` (default) is
  byte-for-byte the v1.6 single-file behavior. A log written in
  single-file mode and read in sharded mode (or vice versa) must
  behave sanely *(open, §5.4)*.

**Open design questions:** §5.1 (surface: parameter vs. subclass),
§5.2 (shard identity), §5.3 (dead-shard reaping), §5.4 (mode
cross-compatibility).

### 4.2 ID-vs-name freshness split (proposed: alpha.2)

**Problem.** v1.6.0-beta.1's per-class TTLs treat `"collection"` as
one class covering both `known_collection_ids` and
`known_collection_names`. But an ID and a name age differently: a
Figma variable-collection ID is stable for the collection's
lifetime, while its display name can be renamed between builds. An
operator may legitimately want `collection_id` hints to stay fresh
for hours while `collection_name` hints expire in minutes.

**Proposed design.** Extend the `freshness_window_overrides` key
vocabulary — no new parameter, no new symbol:

```python
# Proposed — additive key vocabulary.
report = ff.validate_mcp_plan(
    plan, prior_state=prior,
    freshness_window_overrides={
        "collection_id":   3600,   # stable → 1 hour
        "collection_name":  300,   # mutable → 5 minutes
        "component":        300,
    },
)
```

- **New keys** `"collection_id"` and `"collection_name"` map to
  `known_collection_ids` and `known_collection_names` respectively.
- **`"collection"` is preserved as a both-cover alias.** If an
  operator passes `{"collection": 3600}` (the v1.6 spelling), it
  continues to apply to *both* sub-classes. Resolution precedence
  *(open, §5.5)*: most-specific key wins
  (`collection_id` > `collection` > `freshness_window_seconds`).
- **Backward compatibility.** An operator who never uses the new
  keys sees identical v1.6 behavior. Scalar mode
  (`overrides=None`) remains byte-for-byte v1.5.0-alpha.1.
- **Warning text** distinguishes the sub-class
  (`"collection_id hints are …"` vs `"collection_name hints
  are …"`), so the operator can see *which* refinement is stale.

**Open design question:** §5.5 (key resolution precedence when both
`"collection"` and a sub-key are present).

### 4.3 Compositional design (proposed)

The two features are independent — sharding touches the transport's
telemetry persistence, the freshness split touches the validator —
and compose without interaction:

```python
# Sharded CI log feeding a window suggestion; finer freshness on validate.
log = ff.ObservationLog("hist.jsonl", max_records=200, shard_per_process=True)
window, _ = ff.AdaptiveConcurrency().suggest_window(log.read_recent())  # v1.6
ff.PlanRunner().run(
    plan, concurrent=True,
    freshness_window_overrides={"collection_id": 3600, "collection_name": 300},
)
```

## 5. Open design questions (resolve before the named milestone)

### 5.1 *(RESOLVED — gates alpha.2)* Sharding surface — parameter or subclass?

**Resolution: (A) `shard_per_process: bool` parameter on
`ObservationLog`.** Honors the +0-symbol discipline; the mode is a
constructor flag, read/append signatures unchanged. If, during
alpha.2, the sharded read path (glob + merge) proves to entangle the
single-file path beyond clean internal separation, the fallback is a
private helper extraction — *not* a public subclass — so the API
delta stays +0. Approved by operator 2026-05-30.

### 5.2 *(RESOLVED — gates alpha.2)* Shard identity

**Resolution: `f"{pid}-{host_token}-{start_token}"`** where
`host_token` is a short stable hash of the hostname and `start_token`
is a per-process nonce (process start time or a UUID minted once at
first sharded append). This is unique per concurrent writer across a
shared mount and robust against pid reuse. A per-instance UUID was
considered (§5.2 original) but rejected: it would mint a new shard
per `ObservationLog` *instance* rather than per *process*, multiplying
shard count under code that constructs several logs. Approved by
operator 2026-05-30.

### 5.3 *(RESOLVED — gates beta.1)* Dead-shard reaping

**Resolution: age-based reaping folded into `compact()`** — drop
shards untouched for longer than a conservative default window, with
an operator override. A liveness probe was rejected (fragile across
hosts); leaving reaping entirely to the operator was rejected (the
shard set would grow unbounded by default). Approved by operator
2026-05-30.

### 5.4 *(RESOLVED — gates alpha.2)* Mode cross-compatibility

**Resolution: sharded read globs `history*.jsonl` and treats a bare
`history.jsonl` as one more shard.** A mode switch never silently
drops history. Approved by operator 2026-05-30.

### 5.5 *(RESOLVED — gates alpha.1)* Freshness key precedence

**Resolution: most-specific wins.** When `freshness_window_overrides`
contains both `"collection"` and `"collection_id"`, the sub-key wins
for ID hints; `"collection"` covers `collection_name` if no
`"collection_name"` key is present. This mirrors the existing
scalar-fallback precedence (`override → scalar → skip`) extended one
level (`sub-key → "collection" → scalar → skip`) and is the least
surprising. Approved by operator 2026-05-30.

## 6. Explicitly out of scope (re-affirmed from RFC v1.6 §6)

- **Process-pool concurrency variant.** Re-affirmed **rejected**.
  The v1.6 concurrency model assumes I/O-bound dispatch (Figma MCP
  round-trips), where threads overlap correctly. A process pool
  would force dispatch callables and their returns to be picklable —
  a heavy constraint for a speedup no use case needs. This stays
  rejected until a concrete CPU-bound dispatch use case appears.
- **Live-Figma integration test.** Re-affirmed **deferred** to
  operator pilot. The no-network test environment cannot run it; the
  mock-server suite plus wall-clock parallelism probes reach
  functional parity. Continues the v1.1–v1.6 precedent.

## 8. The greenlight decision — RESOLVED

v1.7 is small and not forced, so this section surfaced the *option
not to build it*. The three honest paths were:

1. **Build v1.7 as scoped** — freshness split + sharding, full line.
2. **Build only the freshness split** — the smaller, lower-risk
   item; sharding waits for an operator who hits the contention
   ceiling.
3. **Declare v1.x mature and stop** — v1.6 is complete and stable.

**Decision (operator, 2026-05-30):** Path 3 is declined (we build);
the leanings in §5 are approved. Between Paths 1 and 2, the line
proceeds **freshness-split-first** — the intersection of both paths.
alpha.1 ships the ID-vs-name freshness split (the Path 2 deliverable,
and Path 1's first step). After alpha.1, the Path 1-vs-2 choice —
whether per-process sharding follows (Path 1, → alpha.2/beta.1/GA) or
v1.7.0 ships as a freshness-only GA (Path 2) — is made on its merits,
informed by whether a sharding need has materialized. This honors
"build something, but only what's justified" without committing to
speculative sharding before alpha.1 is in hand.

### Post-alpha.1 decision — RESOLVED (Path 1)

**Decision (operator, 2026-05-30, after alpha.1 shipped):** the line
proceeds on **Path 1** — per-process sharding follows the freshness
split. alpha.2 shipped the sharding (`shard_per_process`, lock-free
appends, merged reads), and beta.1 shipped dead-shard reaping
(`compact(reap_after_seconds=...)`), discharging the full RFC v1.6
§6 tail. The freshness-split-first sequencing paid off exactly as
intended: alpha.1 was decision-independent work (valuable under
either path), and by the time the Path 1-vs-2 choice was made, the
split was already shipped and de-risked — so the only remaining
question was the genuinely larger sharding work, decided on its own
merits. v1.7.0 GA closes the line at **+0 public symbols**.
