# RFC — figma-forge v1.x Maturity & Stability Declaration

| | |
|---|---|
| **Status** | **Accepted — Active Policy** (2026-05-30) |
| **Document type** | Maturity declaration — *not* a feature release |
| **Applies to** | The entire v1.x line: v1.0.0 → v1.7.0, and every future v1.x release |
| **Complements** | `v1.0.0-stable-api.md` (the API freeze); this document declares the *feature set* complete, which the freeze did not |
| **Supersedes** | Nothing |
| **VERSION at declaration** | 1.7.0 (this document does not bump VERSION — it is policy, not code) |

> **Why this is not an RFC in the usual sense.** Every prior RFC in
> this directory (v0.3 → v1.7) proposed or recorded *work* — code that
> shipped. This document proposes no code. It is a **charter**: it
> states, formally and with evidence, that the v1.x line has reached
> feature-completeness, and it defines the maintenance contract that
> governs the line from here. It is written in the project's RFC form
> because every load-bearing decision in figma-forge has been recorded
> as an RFC, and declaring maturity is the most load-bearing decision
> of all.

---

## 1. Purpose

figma-forge began (v0.2.x) as a tool to operationalize a design system
into Figma. Across eight minor releases it became a **design-system-
agnostic protocol** with a frozen public API, a three-channel transport
layer, a self-tuning reference runtime, and a durable, scale-out
observation substrate. Each release discharged the deferral list of the
release before it. After v1.7.0, **there is no deferral list left** —
the v1.4, v1.5, and v1.6 deferral tails are all cleared, and the only
standing item is an integration test that cannot run in the development
environment.

When a project reaches the point where its own backlog is empty and its
remaining work is "confirm in production what the test suite already
proves," continuing to invent features is not engineering discipline —
it is feature-chasing. The disciplined act is to **declare the line
complete, freeze the feature surface, and enter maintenance mode**.

This document makes that declaration and defines what "maintenance
mode" means precisely enough that a future contributor (or a future
session) can tell, for any proposed change, which release class it
belongs to — or whether it belongs in v1.x at all.

---

## 2. The declaration

> **figma-forge v1.x is stable and feature-complete.**
>
> The public API (48 symbols, `API_VERSION = "1.0"`) is frozen under
> the v1.0.0 semver commitment and has not broken once across twelve
> releases. The core capability set — discovery, token import,
> foundations, components, migration, Code Connect, publish audit,
> auto-remediation, orchestration, bundle manifest, audit diff/trend,
> the three-channel transport layer, the self-tuning concurrency
> runtime, and the durable scale-out observation log — is **complete**.
>
> From this point, the v1.x line is in **maintenance mode** (§6): it
> accepts bug fixes and documentation (patch), the results of the
> live-Figma pilot (patch/minor), and *only* demand-driven additive
> features justified by a real, encountered need (minor). It does not
> accept speculative features. Breaking changes are out of scope for
> v1.x entirely and would require a v2.0 line with its own RFC (§8).

This declaration is **honest about its one caveat**: the code is
feature-complete, but one acceptance criterion — the live-Figma
integration test against a real PAT (§7) — has been deferred at every
GA from v1.1 through v1.7 because the test environment has no network.
"Feature-complete" here means *the features are built and proven
against the mock-server suite to functional parity*; it does not claim
real-network soak has occurred. That single confirmation is the one
piece of forward work this charter explicitly keeps open.

## 3. Evidence of maturity

### 3.1 The release arc

| Version | Theme | Public symbols | Net API change |
|---|---|---|---|
| v1.0.0 | Stable API + plugin ecosystem | 22 | freeze baseline |
| v1.1.0 | Transport layer | 32 | +10 |
| v1.2.0 | Transport maturation | 36 | +4 |
| v1.3.0 | Operational hardening | 39 | +3 |
| v1.4.0 | Self-tuning + reference runtime | 45 | +6 |
| v1.5.0 | Durability + smoothing | 46 | +1 |
| v1.6.0 | Dispatch + concurrency maturation | 48 | +2 |
| v1.7.0 | Granularity + scale-out | 48 | +0 |

**Two invariants held across the entire arc:**

1. **`API_VERSION` never changed** — it has read `"1.0"` for all twelve
   releases. Not one minor version forced a wire-format or contract
   revision.
2. **Every API change was additive** — 22 → 48 symbols, zero breaking
   changes, zero retired symbols. The semver commitment of v1.0.0 was
   honored without exception.

The trajectory itself is evidence of maturity: the additive delta
shrank from +10 (v1.1) to +0 (v1.7). The last two releases (v1.5 at +1,
v1.7 at +0) demonstrated that the project had reached the point where
new capability attaches to *existing* objects as fields and parameters
rather than requiring new ones — the signature of a saturated design.

### 3.2 The deferral lists are empty

Each release carried forward a short list of deferred work. As of
v1.7.0:

- **RFC v1.4 §6** (self-tuning / reference-runtime deferrals) —
  discharged by v1.6.0 (the closure release).
- **RFC v1.5 §6** (durability mitigations) — discharged by v1.6.0.
- **RFC v1.6 §6** (per-process `ObservationLog` files, ID-vs-name
  freshness split) — discharged by v1.7.0.

What remains is **not** a deferral list; it is a single standing
integration test (§7) and one explicitly *rejected* idea (the
process-pool concurrency variant, declined in RFC v1.6 and not revived).

### 3.3 The test surface

- **465 / 465** total (457 pytest + 8 skill-verification gates).
- Prior-suite invariance was verified at **every** milestone of the
  v1.5, v1.6, and v1.7 lines — each new feature was proven not to
  perturb the existing suite before it shipped.
- Behavioral smoke tests (real wall-clock parallelism, monkeypatched
  lock-call counters proving lock-free shard appends, chronological
  cross-shard merge) backstopped the unit tests for the concurrency and
  durability features, where "the test passes" and "the behavior is
  correct" are not the same claim.

### 3.4 The completed stories

Each subsystem reached a natural terminus:

- **Transport** (v1.1–v1.2) — three channels (MCP, REST, plugin), a
  capability matrix, a selection decision tree. Complete.
- **Operational hardening** (v1.3) — backoff, error translation, batch
  policy. Complete.
- **Reference runtime + self-tuning** (v1.4) — the plan runner,
  adaptive concurrency recommendation. Complete.
- **Durability + smoothing** (v1.5) — the observation log, cross-build
  window smoothing. Complete.
- **Dispatch + concurrency** (v1.6) — `DispatchResponse`'s two unified
  failure channels, layered parallel execution. Complete.
- **Scale-out** (v1.7) — per-process sharding, dead-shard reaping,
  ID-vs-name freshness granularity. Complete.

## 4. What "feature-complete" means (and does not)

"Feature-complete" is a precise claim here, not a slogan:

**It means:**

- The core protocol — the twelve modes, the three channels, the output
  contract, the 19-gate publish checklist — is closed. No new mode,
  channel, or gate class is planned.
- The reference runtime's transport, concurrency, durability, dispatch,
  and scale-out concerns are each resolved to a natural terminus (§3.4).
- The public API surface is frozen at 48 symbols. New public symbols are
  no longer the default response to a feature request; the default is
  "attach to an existing object, or do not add it."

**It does not mean:**

- *Frozen forever.* A real, encountered need can still justify an
  additive minor release (§6). The bar is "an operator hit a wall," not
  "this would be nice."
- *Bug-free.* Maintenance mode exists precisely to fix defects found in
  use.
- *Fully soaked in production.* The live-Figma pilot (§7) is the one
  open confirmation.
- *Incapable of a v2.0.* If a genuinely breaking improvement becomes
  warranted, it is a v2.0 question (§8), not a v1.x one.

The distinction that matters: **v1.x's feature surface is closed to
speculation, open to necessity.** The "spec minimalism / indirgenemezlik
testi" discipline that governed every release — add a public symbol only
when a genuinely new object is irreducibly required — now governs the
whole line: add a *feature* only when a real need is irreducibly present.

## 5. Stability guarantees

For the life of the v1.x line, figma-forge commits to:

1. **API permanence.** The 48 public symbols in `figma_forge.__all__`
   retain their names and signatures. Fields and keyword parameters may
   be *added* (append-only); none will be removed or have its meaning
   changed. This extends the v1.0.0 freeze from "frozen interfaces" to
   "frozen *and complete* interfaces."
2. **`API_VERSION = "1.0"`.** The contract version does not change
   within v1.x. A change here would, by definition, be a v2.0 event.
3. **Backward compatibility.** Any v1.x release runs any artifact,
   plan, or configuration produced by any earlier v1.x release. The
   mode-cross-compatibility design of v1.7 sharding (a sharded reader
   transparently consumes a single-file log) is the template: new
   mechanisms accommodate old data, never the reverse.
4. **Default-preserving change.** New parameters default to the prior
   behavior. `shard_per_process=False`, `freshness_window_overrides=None`,
   the one-week reap threshold preserving fresh shards — every v1.5–v1.7
   addition shipped this way, and the line will continue to.
5. **RFC-governed evolution.** Any minor addition (§6) is recorded in an
   RFC before it ships, continuing the project's discipline.

## 6. The maintenance-mode contract

From v1.7.0 onward, every proposed change maps to exactly one release
class:

### Patch (v1.7.x) — always welcome

- Bug fixes (defects found in use).
- Documentation corrections and clarifications.
- Test additions that cover existing behavior.
- **Live-Figma pilot fixes** — if the pilot (§7) surfaces a discrepancy
  between mock-server and real-network behavior, the fix is a patch
  (the feature exists; only its real-world fidelity is being corrected).
- No public API change; no behavioral change to documented contracts.

### Minor (v1.8.0+) — demand-driven additive only

- A new capability is added **only** when a real, encountered operator
  need justifies it — not on speculation.
- Strictly additive: new symbols (if irreducible), new fields, new
  keyword parameters, all default-preserving (§5.4).
- Recorded in an RFC first, with the triggering need stated explicitly.
- The bar, restated: *someone hit a wall in production.* "This would be
  elegant" or "other tools have it" does not clear it.

### Major (v2.0.0) — out of scope for v1.x

- Any breaking change — a removed or renamed symbol, a changed default,
  an `API_VERSION` bump, a wire-format revision.
- **Not currently planned.** A v2.0 line would require its own
  motivating RFC establishing why the break is warranted and what it
  buys (§8).

### Decision procedure

> For a proposed change, ask in order:
> 1. Does it break anything (signature, default, format)? → **v2.0** (§8); stop.
> 2. Does it fix a defect or correct docs/tests / pilot fidelity? → **patch**.
> 3. Does it add capability for a *real, encountered* need? → **minor**, RFC-first.
> 4. Otherwise (speculative, "nice to have") → **decline**; record the idea, do not build it.

Step 4 is the point of this charter. A mature project's most common
correct answer to "should we build this?" is "not yet — no one needs it
yet."

## 7. The single open item — live-Figma pilot

One acceptance criterion has been deferred at every GA from v1.1
through v1.7: **a live-Figma / MCP integration test against a real
Figma file under a real PAT.**

- **Why deferred:** the development and test environment has no outbound
  network to Figma's API. The mock-server suite (`tests/fixtures/
  mock_figma_server.py`) reaches functional parity — it exercises the
  REST channel, error translation, backoff, and batch policy against a
  faithful mock — but real-network confirmation is a different claim.
- **How it closes:** an operator runs figma-forge against a real Figma
  file with a real PAT, in each of the three channels, and confirms the
  build. This is a **pilot**, not a code change. If it succeeds, the
  criterion is met and noted (patch-level documentation). If it surfaces
  a discrepancy, the fix is a patch (§6).
- **Status:** open, owned by operator pilot. It is the only forward work
  this charter keeps.

This is the honest boundary of the maturity claim: **everything
testable in the environment is tested and green; the one untestable
confirmation is explicitly outstanding.**

## 8. What would trigger a v2.0 line

v2.0 is not planned. This section exists so that, if the question ever
arises, the bar is already written. A v2.0 line would be warranted only
by a change that *cannot* be made additively — for example:

- **A wire-format or contract revision** that the `API_VERSION = "1.0"`
  promise cannot absorb (e.g., a fundamentally different audit JSON
  schema that a `$schema` sidecar cannot bridge).
- **A transport model change** that breaks the `AbstractFigmaTransport`
  ABC's signature — e.g., if Figma's API surface changed so
  fundamentally that the three-channel abstraction no longer held.
- **A removal** of a capability that has become actively harmful to keep
  (none is known or foreseen).

Absent such a forcing function, the correct path for every improvement
is additive within v1.x (§6 minor) — and the empty deferral list (§3.2)
suggests no such forcing function is on the horizon. **The most likely
future of figma-forge is a long, stable v1.x maintenance life**, with
occasional demand-driven minors and the eventual closure of the
live-Figma pilot.
