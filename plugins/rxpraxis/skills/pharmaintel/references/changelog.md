# pharmaintel — Full Changelog

> **Purpose of this file:** Complete historical release record for the pharmaintel skill, extracted from `SKILL.md §Versioning` in v6.0.0 to prevent context-window truncation of the core entry point document. SKILL.md itself retains only the current version + last 3 release summaries + a pointer to this file. This separation was motivated by the v5.0.0 production test (T-DXd asset profile, 2026-04-16) in which the runtime reported the SKILL.md changelog as "ending at v3.0.0" — a context truncation artifact caused by the monolithic SKILL.md size of ~637 lines.
>
> **Lazy-loading discipline:** Claude loads this file ONLY when (a) the user explicitly asks about skill version history, upgrade path, feature provenance, or deprecation timeline; (b) the user asks "what changed in version X"; (c) the validator needs to cross-reference a specific gate's introduction release. For routine pharmaintel invocations, this file should NOT be loaded — the core `SKILL.md` + `sources-catalog.md` + `triangulation.md` + `query-patterns.md` + `generic-by-default.md` foundational layer is sufficient for task execution.
>
> **Release canonical ordering:** Most-recent-first (reverse chronological). Each entry is self-contained — no cross-entry dependencies. Entry format standardized from v1.7.0 onward; earlier entries (v1.0.0–v1.6.0) use single-paragraph format.

- **v6.0.0 (2026-04-16)**: **MAJOR DOCUMENTATION + ARTICLE 5 CLARIFICATION RELEASE** — Two coordinated improvements motivated by v5.0.0 production test findings.
  - **(A) SKILL.md Modularization (context-window truncation fix):** The monolithic ~637-line SKILL.md (v5.0.0) exceeded the practical reliability threshold for skill-runtime context loading. v5.0.0 production test revealed that runtime reported SKILL.md changelog as "ending at v3.0.0" despite v4.0.0 + v5.0.0 entries being present locally — diagnosed as context truncation. v6.0.0 refactors SKILL.md by extracting the full release-notes changelog to `references/changelog.md` (this file), leaving SKILL.md §Versioning at ~20 lines (current version + last 3 release summaries + pointer).   - **(B) Article 5 Interpretation Clarification — Query Language ≠ Sub-Protocol Trigger:** v5.0.0 production test (T-DXd raporu, Türkçe query "trastuzumab deruxtecan raporu hazırla") revealed that `sub-protocol-turkey.md` fired despite query content containing ZERO Türkiye-specific terminology (TİTCK, SGK, SUT, etc.). Root cause: runtime interpreted "Turkish language query" as a valid content trigger under Article 5.1 row "Geographic mention in query — YES". This conflates query *language* (writing system / natural language) with query *scope* (semantic content). v6.0.0 codifies a new principle: **query language is NEVER a valid trigger source for a regional sub-protocol**. The correct content trigger must be explicit regional terminology (keywords) or explicit geographic scope (content), not the writing system. Applied to three sub-protocols symmetrically: (i) `sub-protocol-turkey.md` — Turkish query language ≠ trigger; (ii) `sub-protocol-pmda.md` — Japanese query language ≠ trigger; (iii) `sub-protocol-nmpa.md` — Mandarin query language ≠ trigger. `generic-by-default.md` Article 5.1 forbidden-trigger table extended with new row "Query language (writing system / natural language of query)" → NO (forbidden). New Article 5.3 "Language vs scope distinction" added (full principle statement + worked example + symmetric application across PMDA/NMPA/Türkiye). New manifest gate **G61** (query-language-as-trigger audit — validator checks that no auto-trigger rationale cites query language as trigger source). `scripts/validate-report-discipline.py` extended with `check_g22_9()` function (language-trigger pattern detection in `<Auto-Trigger Disclosure>` blocks: regex `(turkish|türkçe|japanese|japonca|mandarin|çince|chinese).{0,40}(language|dil|written|yaz[ıi]lm[ıi]ş).{0,40}(trigger|tetik)`).

## Version Bump Conventions

pharmaintel follows semantic versioning with three bump classes:

- **Patch (x.y.Z):** bug fix, script enhancement, validator improvement, non-behavioral content correction. No breaking changes. Example: v1.0.1, v1.7.1.
- **Minor (x.Y.0):** additive content (new sub-protocol, new reference document, new task playbook, new manifest gate), behavioral refinement (trigger logic clarification within same axis), template/validator feature additions. Backward-compatible. Example: v1.1.0 through v1.9.0, v2.6.0.
- **Major (X.0.0):** new architectural capability layer, new data model, new operational substrate, new deliverable artifact class, or categorical expansion of template architecture. May introduce opt-in behaviors but never breaks existing API surface. Example: v2.0.0 (layered modality template pattern), v2.5.0 (modality suite completion), v3.0.0 (4 coordinated axes), v4.0.0 (10-TA coverage), v5.0.0 (forensic provenance layer), v6.0.0 (SKILL.md modularization + Article 5 clarification).

The v6.0.0 major bump is justified by the **architectural significance of document modularization** (the core entry point for every invocation was restructured) plus the **semantic clarification of Article 5 discipline** (which governs how EVERY auto-trigger is rationalized across all sub-protocols).
